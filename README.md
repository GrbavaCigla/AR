# AR — RISC-V LiDAR Scanner on an FPGA

A complete computer built from scratch on a Cyclone V FPGA: a custom RV32I
processor, its bus, an SDRAM controller, a VGA display pipeline, and a LiDAR
peripheral — plus the C firmware that ties them together into a live 2D room
scanner.

Almost all of the hardware is drawn as Quartus **Block Diagram Files** (`.bdf`)
rather than written in HDL. The `.v` files sitting next to them are generated by
Quartus from the schematics — **the `.bdf` is the source of truth**, and editing
the `.v` by hand will be silently overwritten on the next compile.

## What it does

The LD14P LiDAR spins at ~6 Hz and streams distance readings over UART. The FPGA
receives them, parses the packets, converts polar readings to screen
coordinates in hardware, and hands finished pixel coordinates to the CPU. The
CPU plots them into an SDRAM-backed framebuffer, which is scanned out to a VGA
monitor as a live top-down map of the room.

## Hardware

| Part | Detail |
|---|---|
| FPGA | Cyclone V 5CEBA4F23C7 (Terasic DE0-CV) |
| LiDAR | LDROBOT LD14P — 230400 baud, ~4000 points/s, ~6 Hz rotation |
| Clock | 50 MHz |
| SDRAM | 32 MiB |
| Display | VGA, 800×600, 1 bit per pixel |
| CPU | RV32I, no interrupts, synchronous atomic bus |

## Memory map

The bus decodes on `bus_addr[29:28]`, so each peripheral owns a large aliased
region rather than a tight address window.

| Base | Peripheral |
|---|---|
| `0x0000_0000` | SDRAM |
| `0x1000_0000` | LiDAR |
| `0x2000_0000` | VGA |
| `0x3000_0000` | LED |

### LiDAR register (read)

| Bits | Meaning |
|---|---|
| 31 | valid — data present |
| 29:20 | point index within the current revolution |
| 19:10 | x pixel |
| 9:0 | y pixel |

### VGA register (write)

| Bits | Meaning |
|---|---|
| 31 | pixel value (1 = set, 0 = clear) |
| 30 | swap front/back buffer |
| 19:10 | y |
| 9:0 | x |

## Building

**Firmware** — from `firmware/`, run `just`. This cross-compiles, converts the
binary into a `.mif`, and copies it into the Quartus project as the CPU's
instruction memory image.

**Hardware** — open `hardware/riscv32i processor/Riscv32i.qsf` in Quartus 13.1,
top-level entity `MainScheme`, then compile and program the board.

Firmware changes require both steps: rebuild the firmware first so the `.mif` is
current, then recompile in Quartus so the new image is baked into the bitstream.
